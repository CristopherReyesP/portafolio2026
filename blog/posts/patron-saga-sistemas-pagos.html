Patrón Saga en sistemas de pagos: qué hacer cuando una transacción falla a mitad

En sistemas distribuidos no podemos depender de una única transacción de base de datos. Saga permite coordinar operaciones y compensarlas cuando algo falla.

25 de septiembre de 2026 3 min de lectura Cristopher Reyes

Cuando una operación vive completamente dentro de una base de datos, mantener consistencia suele ser relativamente sencillo.

Podemos iniciar una transacción:

BEGIN

ejecutar varias operaciones y finalmente hacer:

COMMIT

Si algo falla:

ROLLBACK

El problema aparece cuando una operación de negocio depende de varios servicios.

Imaginemos un pago que necesita realizar varias acciones:

  1. Pago
  2. Débito
  3. Crédito
  4. Actualización de cheque
  5. Registro de operación

Cada una puede pertenecer a un servicio diferente.

En ese momento ya no existe una única transacción de base de datos capaz de envolver todo el proceso.

El problema

Supongamos este flujo:

  1. El débito se procesa correctamente.
  2. El crédito se procesa correctamente.
  3. El servicio que actualiza el cheque tarda demasiado.
  4. El orquestador recibe un timeout.

Ahora tenemos un problema.

¿La operación falló realmente?

No necesariamente.

El timeout únicamente nos dice que no recibimos respuesta dentro del tiempo esperado.

El servicio podría haber terminado correctamente unos segundos después.

Por eso una de las ideas más importantes trabajando con sistemas distribuidos es:

Un timeout no es sinónimo de fallo.

¿Qué es Saga?

Saga es un patrón para coordinar una operación de negocio compuesta por múltiples transacciones independientes.

En lugar de depender de una gran transacción distribuida, cada servicio ejecuta su propia operación.

Ejemplo:

  1. Pago
  2. Débito
  3. Crédito
  4. Cheque
  5. SUCCESS

Si uno de los pasos falla, ejecutamos operaciones compensatorias.

Por ejemplo:

  • Débito realizado
  • Crédito realizado
  • Cheque falla

entonces podemos necesitar:

  • Reversa de crédito
  • Reversa de débito

La compensación no es un rollback tradicional.

Es una nueva operación de negocio que intenta revertir el efecto de otra operación ya confirmada.

Estados explícitos

Una Saga necesita conocer el estado del proceso.

Estados simples pueden ser: INITIATED SUCCESS ERROR
Y para las compensaciones: PENDING RETRYING FAILED COMPLETE

Persistir estados permite responder preguntas importantes:

  • ¿qué pasos terminaron?
  • ¿qué paso falló?
  • ¿qué compensaciones faltan?
  • ¿se puede reintentar?
  • ¿la operación ya terminó?

Sin esta información, diagnosticar un fallo distribuido se vuelve muy difícil.

Idempotencia

Una operación distribuida puede repetirse.

El cliente puede reintentar.

El gateway puede reintentar.

El orquestador puede volver a ejecutar una llamada.

Por eso las operaciones importantes deberían ser idempotentes.

Una operación idempotente permite ejecutar la misma solicitud varias veces sin producir efectos adicionales.

Ejemplo: Una petición:

procesar débito operación=ABC123

no debería generar dos débitos si se recibe dos veces.

La segunda petición debería detectar que ABC123 ya fue procesada y devolver el resultado correspondiente.

Compensaciones

Las compensaciones deben diseñarse desde el inicio.

No es suficiente implementar:

hacerDébito()

También debemos pensar:

revertirDébito()

Lo mismo ocurre con:

hacerCrédito()
revertirCrédito()

El diseño cambia cuando asumimos que cualquier parte puede fallar.

Reintentos

No todos los errores deben provocar inmediatamente una compensación.

Algunos errores son temporales.

Por ejemplo:

  • conexión momentáneamente caída
  • servicio temporalmente saturado
  • bloqueo de base de datos
  • error de red

En esos casos puede ser válido aplicar retries.

Pero un retry debe tener:

  • número máximo de intentos
  • espera controlada
  • idempotencia
  • observabilidad

IMPORTANTE

Un retry infinito simplemente transforma un fallo en otro tipo de incidente.

Conclusión

Saga no elimina la complejidad de los sistemas distribuidos.

La hace explícita.

Cuando una operación atraviesa múltiples servicios debemos pensar desde el principio en:

  • estados
  • idempotencia
  • compensaciones
  • retries
  • timeouts
  • observabilidad

En sistemas críticos, el camino feliz es apenas una parte del diseño.

La verdadera arquitectura comienza cuando preguntamos:

¿qué ocurre si este paso falla?
